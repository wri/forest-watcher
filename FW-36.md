## Phase 1 — Merge PR #6 branch and restore extractNativeLibs

### Why `android:extractNativeLibs="false"` must be kept

Google Play's 16 KB page-size requirement has two distinct halves:

1. **ELF segment alignment** — `.so` files must have LOAD segments aligned to ≥ 16 KB.
   This is addressed by building with NDK r27+.

2. **ZIP alignment** — native libs must be stored uncompressed and page-aligned inside
   the APK so the OS can `mmap()` them directly from the ZIP without extraction.
   This requires either:
   - `android:extractNativeLibs="false"` in `AndroidManifest.xml`, **or**
   - `packagingOptions { jniLibs { useLegacyPackaging = false } }` in `build.gradle`

   The attribute tells the Android package installer not to extract `.so` files to the
   filesystem at install time. On API 23+ the OS can load them directly from the APK
   via `mmap`, which is required for 16 KB page-size devices to function correctly.

   PR #6 removes this attribute — likely an accidental conflict with our branch's prior
   addition. Without it, the `zipalign -P 16` check in `scripts/check-16kb-android.sh`
   will pass but devices with 16 KB page sizes will fail to load native libraries at
   runtime on API 23+ (Android 6+).

**Action:** After merging PR #6's branch, immediately re-add `android:extractNativeLibs="false"`
to the `<application>` tag in `AndroidManifest.xml`.

### Steps

```bash
# 1. Fetch the PR #6 branch
git fetch origin kg-react-native-upgrade-t1

# 2. Merge into our branch (or rebase — confirm with team)
git merge origin/kg-react-native-upgrade-t1 --no-ff -m "chore: merge RN 0.79 / NDK r28 upgrade from PR #6"

# 3. Resolve conflicts (expected in: android/build.gradle, AndroidManifest.xml,
#    package.json, patches/*, yarn.lock)

# 4. Restore extractNativeLibs (PR #6 removes it — re-add immediately after merge)
#    In android/app/src/main/AndroidManifest.xml, ensure <application> contains:
#    android:extractNativeLibs="false"

# 5. Re-run yarn to update lockfile with merged dependency tree
yarn install

# 6. Verify patches apply cleanly
yarn prepare
```

## Phase 2 — NDK r28 validation

### 2a. Confirm NDK r28 is installed

```bash
ls $ANDROID_HOME/ndk/
# Expected: 26.1.10909125  27.3.13750724  28.2.13676358
# If 28 is missing:
$ANDROID_HOME/cmdline-tools/latest/bin/sdkmanager "ndk;28.2.13676358"
```

### 2b. Realm native build with NDK r28

The regenerated `patches/realm+12.13.2.patch` pins the Realm native build to the root
project's NDK and excludes `libreactnative.so` from the Realm AAR. This is required for
NDK r28 because r28 no longer exports `libreactnative.so` from the RN AAR, and Realm's
CMakeLists previously linked against it.

**Validation:** Run `yarn android:sideload:build` and confirm no CMake/linker errors.
If errors appear referencing `libreactnative`, the patch has not applied — re-run `yarn prepare`.

### 2c. Run the 16 KB compliance checker

```bash
yarn android:sideload:build
yarn android:check-16k
# All .so files in lib/arm64-v8a/ and lib/x86_64/ must print "ALIGNED"
# ZIP alignment check must show "Verification succeded"
```

**Known pre-existing issue:** `@react-native-mapbox-gl/maps` 8.6.0-beta.0 bundles
Mapbox Android SDK 9.x (2020) `.so` files that are 4 KB-aligned. These will show as
`UNALIGNED` in the check. This is a pre-existing limitation of the Mapbox SDK version
and cannot be resolved without upgrading to Mapbox Maps SDK v10+. Document and accept
this for this release; flag for FW-37.

## Phase 3 — React Native 0.76 → 0.79 compatibility

### 3a. React 19 breaking changes

React 19 removes legacy context API and changes ref behaviour. Audit these areas:

- **Class components with `contextTypes`** — search codebase:
  ```bash
  grep -rn 'contextTypes\|childContextTypes\|getChildContext' app/
  ```
- **String refs** (`ref="myRef"`) — already partially addressed in the Mapbox patch;
  confirm no remaining occurrences:
  ```bash
  grep -rn 'ref="' app/
  ```

### 3b. RN 0.79 removed APIs

RN 0.79 finalises the removal of several Paper-era APIs. Check for:

| Removed API | Replacement | Where to look |
|---|---|---|
| `StyleSheet.flatten` edge cases | Same API, stricter types | `app/components/` style files |
| `AccessibilityInfo.fetch` | `AccessibilityInfo.isScreenReaderEnabled()` | Search `AccessibilityInfo` |
| `StatusBar.currentHeight` (Android) | `useWindowDimensions` / `StatusBar.getHeight()` | Layout components |

```bash
grep -rn 'AccessibilityInfo\.fetch\|StatusBar\.currentHeight' app/
```

### 3c. `react-native-datepicker` 1.7.2 (unpatched — HIGH RISK)

This library uses `ViewPropTypes` from React Native, which was removed in RN 0.73+.
The existing `deprecated-react-native-prop-types` shim may cover it, but RN 0.79
tightens the shim boundaries.

**Used in:** `app/components/common/form-inputs/date/index.js`

**Options (choose one):**
1. **Patch it:** Add `patches/react-native-datepicker+1.7.2.patch` replacing all
   `ViewPropTypes` imports with `require('deprecated-react-native-prop-types').ViewPropTypes`
2. **Replace it:** Swap `react-native-datepicker` for `@react-native-community/datetimepicker`
   (maintained, RN 0.79 compatible). Requires updating `app/components/common/form-inputs/date/`.
3. **Test first:** Build and run the report form on a device — if the date picker
   renders without error under RN 0.79, the shim is covering it and no action is needed.

**Recommended:** Option 3 first; fall back to Option 1 if it crashes.

### 3d. `react-native-actions-sheet` 0.5.6 (unpatched — MEDIUM RISK)

Version 0.5.6 is from 2021 and has known Paper bridge assumptions.

**Used in:** `app/components/common/dropdown/index.js`

**Options (choose one):**
1. **Upgrade:** `react-native-actions-sheet` `^0.9.x` or `^1.x` has RN 0.79 support.
   Requires API change audit (the `show/hide` API changed in v0.6+).
2. **Patch it:** Inspect the build error (if any) and patch the specific Kotlin class.
3. **Test first:** Build and open a dropdown — if no crash under RN 0.79, accept as-is.

**Recommended:** Option 3 first; upgrade to latest 0.x if it fails.

## Phase 4 — react-native-navigation v7 → v8 migration

RNN v8 is a major release. The patch in PR #6 addresses only the Android build-time
Kotlin compatibility issue (`ModalContentLayout`). The JS/navigation API surface also
changed.

### 4a. Breaking API changes in RNN v8

| Change | v7 behaviour | v8 behaviour |
|---|---|---|
| `options.topBar.rightButtons` | Array of `{ id, text, ... }` | Same — no change |
| `NavigationButtonPressedEvent` | `{ buttonId }` | Same — no change |
| `Navigation.showOverlay` depth | `passProps` forwarded | Requires explicit `interceptTouchOutside` |
| `ModalContentLayout` gesture signature | Two overloaded `onChildStartedNativeGesture` | Merged to single with nullable `child` — patched |
| `handleException` signature | `Throwable?` | `Throwable` non-null — patched |

The v8 patch in PR #6 covers items 3–5. Items 1–2 are unchanged. **No JS call site changes required** based on the diff, but full flow testing is essential.

### 4b. Navigation flows to validate

There are **19 `setRoot`/`setStackRoot`/`showOverlay`/`dismissAllModals` calls**,
**21 `showModal` calls**, and **51 `Navigation.push` calls** in the codebase. All
registered screens (31 total in `app/screens/index.js`) must be validated.

**Prioritised test flows:**

| Priority | Flow | Navigation APIs exercised |
